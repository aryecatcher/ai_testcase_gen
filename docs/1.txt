1. 系统运行环境与基础设施规格
为确保 AI 模型推理的稳定性与数据安全性，系统采用私有化部署模式 。

·操作系统 (OS)：
服务端：推荐使用 Ubuntu 22.04 LTS 或 CentOS 7.9 及以上 Linux 内核系统，以支持 Docker 容器化部署及 NVIDIA 驱动环境 。
客户端：基于 Web 端访问，兼容 Chrome 90+、Edge 等主流浏览器。

·硬件加速：
由于涉及大语言模型（LLM）推理与微调，建议部署环境配备 NVIDIA A100/H100 或同等算力的 GPU 显卡，显存不低于 40GB 。

·部署架构：
支持 K8s 集群化部署，实现需求解析服务、图谱计算服务、LLM 推理服务的逻辑解耦 。


2. 核心工作流：从需求到用例的每一步
2.1第一步：需求输入与标准化 (Requirement Ingestion)

2.1.1多源格式读取：系统监听上传接口，接收 Word (.docx)、Excel (.xlsx)、JSON 或 Swagger/OpenAPI 接口文档 。
·监听与接收：系统后台建立基于 RESTful 的上传服务，监听 POST /api/v1/requirements/upload 接口 。
·格式自动分流：
非结构化文档 (.docx, .xlsx)：调用 Apache Tika 或 Python-Docx 库读取文本流，过滤页眉、页脚及冗余样式信息 。
结构化文档 (JSON, YAML)：直接解析对象树，主要针对 Swagger 或 OpenAPI 接口定义文件 。

·OCR 辅助（可选扩展）：若 Word 中包含图片格式的流程图，系统调用 OCR 引擎（如 Tesseract 或 PaddleOCR）提取图片文字，确保信息无遗漏 。

2.1.2 内容清洗与转换：利用 NLP 技术将非结构化文本实时转化为标准 JSON 结构，通过实体识别（NER）精准锁定“检验项目”与“技术要求” 。
·文本预处理：
分词与去噪：去除文档中的停用词（如“的”、“了”等非关键性连接词）。
断句处理：基于语义边界将长段落拆分为独立的“需求原子桩”。
·深度语义提取 (NER & SRL)：
命名实体识别 (NER)：利用预训练模型识别出“角色”（如：管理员）、“操作”（如：重置密码）、“参数”（如：手机号）及“数值约束”（如：8-16位） 。
语义角色标注 (SRL)：分析句子中的谓语关系，明确“谁”对“什么”执行了“什么动作”，并满足“什么条件” 。
核心字段映射：将解析结果自动归类至标准 JSON 的 req_spec 字段，重点锁定 “检验项目”（功能点）与 “技术要求”（验收标准） 。

2.1.3 规范化引导：若输入文档解析置信度低于 80%，系统自动触发引导提示，要求商务/产品人员按预设模板补全关键信息 。
·置信度评分计算：计算公式定义为：Confidence=EmatchedErequired。其中Ematched 为成功识别的核心实体（如操作、输入、预期），Erequired 为标准用例模版所需的必备要素 。
·阈值触发机制：
若 Confidence≥80%：系统自动进入 AI 处理层进行场景生成 。
若 Confidence<80%：系统阻断流程，并向前端返回报错信息 。
·引导式补全：
缺失项高亮：在界面上通过红色加粗提示“技术要求模糊”或“输入参数缺失” 。
模板推送：自动下发《标准需求编写规范模板》，引导商务或产品人员按照“如果 [前提]，执行 [操作]，则 [结果]”的逻辑重写需求 。

2.1.4 输出产物：标准结构化需求桩 (Intermediate JSON)
经过此步骤后，系统生成如下标准化的 JSON 片段，作为下一阶段“AI 处理层”的输入：

JSON

{
"ingestion_metadata": {
"source_file": "创新中心管理系统_V1.docx",
"parsing_confidence": 0.89,
"timestamp": "2026-01-27T21:54:14Z"
},
"extracted_entities": {
"module": "用户权限管理",
"feature": "多因子登录验证",
"constraints": [
{"field": "otp_code", "type": "numeric", "length": 6},
{"field": "retry_limit", "value": 3, "action": "lock_account"}
]
}
}



2.2 第二步：AI 深度语义解析 (AI Processing)
2.2.1实体与角色标注：利用 LLM 结合语义角色标注（SRL）技术，自动提取操作行为（如“点击”）、输入参数（如“密码”）、约束条件（如“错误3次”）及异常场景 。
·实体提取 (NER)：
识别功能点：如“登录”、“支付”、“账户查询” 。
识别输入参数：自动锁定用户输入项，如“手机号”、“验证码”、“密码长度” 。
识别业务约束：精准捕捉量化指标，如“错误3次”、“锁定1小时”、“响应时间 < 2s” 。
·语义角色标注 (SRL) 逻辑建模：
系统通过分析谓语（Action）及其关联角色（Agent/Object）建立行为树 。
示例解析：针对“用户登录时，密码错误3次则锁定账号”：
Agent (主体)：用户 。
Action (动作)：登录 。
Condition (约束/条件)：密码错误、次数=3 。
Result (预期结果)：账户锁定、时长1小时 。
·异常场景识别：
系统不仅识别正常路径，还利用 LLM 挖掘语义中的否定或异常词汇（如“失败”、“不可用”、“超时”），自动生成异常流程测试点 。

2.2.2 提示词 (Prompt) 工程：系统内置动态提示词模板，根据需求类型自动调整 Prompt 策略，以最大化 LLM 的逻辑生成质量 。
·上下文注入 (Context Injection)：
将第一层提取的模块路径（如：用户中心/安全/登录）和优先级（P0）作为背景信息注入 Prompt 。
指令约束：明确要求 LLM 必须输出符合定义的 JSON 结构，包含 steps、expected 和 test_data_sets 。
·测试策略引导 (Methodology Induction)：
数值类需求：自动在 Prompt 中加入“执行边界值分析”指令，要求生成最大值、最小值、空值等测试用例 。
流程类需求：加入“执行因果图/判定表”指令，覆盖多条件组合下的业务路径 。
·知识图谱约束 (KG-Reinforcement)：
将知识图谱中检索到的关联规则（如：手机号号段规则）作为“参考知识”放入 Prompt 模板中，强制 LLM 遵循既定业务规范，避免其产生随机幻觉 。
·迭代优化机制：
系统记录历史人工审核的反馈（如：修改点、删除原因），将纠偏后的优秀范例作为 Few-Shot（少量示例）动态加入 Prompt，实现模型逻辑生成的持续进化 。

2.2.3 分类与优先级评估 (ML Classification)
在生成逻辑的同时，利用机器学习（ML）模型对用例进行属性标注 。
模块归属分类：基于历史数据将生成用例自动归类至对应的业务树节点 。
优先级预测：根据功能点的重要程度和风险等级，自动标记 P0/P1/P2 优先级，辅助测试人员决定执行顺序 。


2.3 第三步：基于知识图谱的场景扩展 (KG Expansion)
2.3.1路径搜索：当系统在第二步完成语义解析后，会获取到一个或多个“核心实体”作为搜索种子 。
·种子节点映射：系统将识别出的功能点（如“支付”）映射为知识图谱中的 “核心节点” (Seed Node) 。
·激活业务场景逻辑层：
底层指令：执行类似于 MATCH (p:Function {name: "支付"})-[:HAS_FLOW]->(flow) 的查询语句 。
深度遍历：系统自动从核心节点出发，沿着“业务流”边缘进行 $N$ 度路径搜索，寻找与其关联的行业标准流程 。

·上下文关联：如果需求文档只提到了“支付成功”，图谱会强制调取与其关联的“前置依赖节点”（如：账户状态检查、实名认证状态） 。

2.3.2子场景补齐：此步骤旨在通过图谱的“联想能力”弥补人工经验的不足，防止测试遗漏 。
·异常路径激活：基于 “业务场景逻辑层”，系统会自动拉取与核心功能相连的所有“异常分支”节点 ：
资金类异常：自动补齐“余额不足”、“账户冻结”、“单日限额触发”等场景 。
通讯类异常：自动关联“支付接口超时”、“第三方回调失败（如微信/支付宝回调丢失）”、“网络中断”等场景 。
·补齐测试桩 (Test Stub Generation)：
对于每一个补齐的子场景，系统会生成对应的逻辑描述片段（如：“当支付请求发出且 30s 未收到回调时，触发补偿查询逻辑”） 。
·场景优先级标注：根据图谱中节点的“权重”标签，自动为补齐的场景标注优先级（如：“余额不足”标记为 P0，“第三方系统瘫痪”标记为 P2） 。

2.3.3 边界约束与防幻觉校验
这是系统的“安全护栏”，确保 AI 生成的用例不脱离现实物理规则和业务逻辑 。
·强制调用规则与约束层：
系统将 AI 初步生成的测试数据（如：输入的手机号）送入 “规则与约束层” 进行拦截校验 。
规则比对逻辑：若 AI 生成的用例中手机号为 10 位，系统会检索图谱中 [:CONSTRAINED_BY] 关系指向的“国家标准-手机号位长”节点（值为 11 位），并触发修正 。
·防幻觉机制执行：
拦截器逻辑：在最终输出 JSON 前，系统会执行一个“幻觉检查循环” 。
示例：如果 LLM 幻想出一个“用户可以用负数金额支付”的场景，图谱中的“金额约束规则”会强制将其拦截并改为正确的边界值（如：0 或 0.01） 。
·输出校准：只有通过了图谱约束校验的逻辑段，才能进入下一阶段的“用例生成层” 。

2.4 第四步：用例自动化生成 (Test Case Generation)
本阶段在系统的“生成引擎模块”中运行，通常基于 Python 环境集成测试方法论算法库。
2.4.1 理论模型套用：从语义到测试矩阵 (Algorithmic Logic)
系统不再仅仅依赖 LLM 的概率生成，而是强制执行经典的测试设计方法论：
·等价类划分算法 (Equivalence Partitioning)：
逻辑实现：针对每个输入参数，系统自动将其划分为：有效等价类（符合需求）和无效等价类（不符合需求）。
系统操作：若参数为“年龄”，范围为 [18,60]。算法自动生成有效点（如 25）及无效点（如 10、70）。
·边界值分析 (Boundary Value Analysis)：
逻辑实现：系统在 Linux 后端计算参数的临界点：min−1,min,min+1,max−1,max,max+1。
应用场景：针对“密码长度 8-16 位”，生成引擎强制产出长度为 7,8,9,15,16,17 的测试向量。
·因果图与判定表 (Decision Table)：
逻辑实现：处理多条件组合（如：用户欠费 AND 账号锁定 -> 无法登录）。
系统操作：通过真值表逻辑确保 2n 种组合路径在逻辑层被全数覆盖，避免组合爆炸或遗漏。
2.4.2数据自动填充引擎 (Data Synthesis Engine)
基于上述理论模型，系统调用数据生成器（如定制化的 Faker 库或正则逆向引擎）生成真实的测试值。
数据类型	生成策略	示例 (针对“用户名”字段)
合法集 (Valid Set)	满足所有约束的最简组合。	test_user_001, Admin_888
非法集 (Invalid Set)	类型错误：数值型输入字符。

长度异常：超出边界。

特殊符号：注入攻击脚本、特殊 Unicode。	NULL, <script>alert(1)</script>, VeryLongName... (超出长度)
关联集 (Correlated)	根据业务逻辑生成的互斥或依赖数据。	已冻结的账户名、已存在的重复名
2.4.3 多维度输出规格 (Multi-dimensional Output)
系统不仅生成文本用例，还根据需求类型同步生成三类输出产物：
·功能测试用例 (Functional)：
重点：详细的操作步骤、预期的 UI 响应、前置依赖环境。
格式：适配飞书多维表格/Excel 的标准字段。
·接口测试用例 (API/Integration)：
重点：自动生成 Request Payload（JSON/XML）、预期状态码（如 200 OK, 403 Forbidden）、返回值 Schema 校验规则。
兼容性：支持导出为 Postman Collection 或 JMeter 脚本片段。
·性能指标场景 (Performance)：
	逻辑抽取：从技术要求中提取 SLA 关键词。
生成产物：定义并发用户数阈值、响应时间基准（如 RT<500ms）、资源利用率红线（CPU > 80% 触发告警）。
2.4.4 系统层执行流 (System Flow)
在底层操作系统与服务调度上，该步骤遵循以下逻辑：
并发处理：生成引擎采用异步队列（如 Celery + Redis），支持同时处理上百条需求的用例并行生成。
持久化存储：生成的中间态 JSON 数据存入 MongoDB 或 PostgreSQL，并关联唯一的需求 ID（Requirement ID），确保版本可溯源。
飞书 API 调用：生成完成后，系统触发 Webhook 或 Open API 调用，将数据流式写入飞书多维表格的特定 AppToken 下。

2.5第五步：分发、审核与反馈闭环 (Feedback Loop)
2.5.1 自动化分发与多平台对接 (Platform Integration)
系统生成的标准 JSON 逻辑将通过适配器转换为不同工具所需的物理格式。
·飞书多维表格（Bitable）深度集成：
身份认证：系统通过 Feishu Open Platform 的 App ID 和 App Secret 获取 tenant_access_token。
动态写入：利用飞书 API (POST /open-apis/bitable/v1/apps/:app_token/tables/:table_id/records)，将 JSON 中的字段（ID、模块、步骤、预期结果、优先级）映射到多维表格的列字段中。
实时同步：支持“增量写入”，即需求变更后，系统自动定位飞书中的旧用例并标记为“待更新”或直接覆盖。
·管理平台兼容性适配 (TestLink/禅道)：
格式转换引擎：
TestLink：将 JSON 转换为符合 TestLink 规范的 .xml 文件（包含 <testcase> 标签）。
禅道 (Zentao)：将 JSON 转换为特定的 .csv 或通过禅道 REST API 直接推送。
·标准化 Excel 导出：
系统预设符合创新中心规范的 Excel 模板（含表头样式、下拉筛选）。用户点击“一键导出”时，系统调用 Python 的 Pandas 或 Openpyxl 库完成样式渲染并下载。
2.5.2 专业化人工审核与纠偏 (Human-in-the-loop)
提供一个直观的 Web 界面，供测试工程师对 AI 生成的内容进行最终确认。
·对比视图 (Traceability View)：
界面左侧显示原始需求文本，右侧显示 AI 生成的用例。系统高亮显示需求中的关键词在用例中的对应位置，确保“所见即所得”。
·在线编辑与操作 (CRUD)：
修改：工程师可以直接修改步骤描述或预期结果。
标记场景：工程师可以标记某条用例为“无效”或“逻辑错误”，并选择错误原因（如：幻觉、规则错误、步骤冗余）。
版本控制：
系统记录用例的“生成版本”与“人工修正版本”，支持一键回滚。

2.5.3 模型进化与知识补齐 (Model Evolution & KG Update)
这是系统的“闭环灵魂”，确保错误不再犯第二次。

·负样本采集与清洗：
系统自动收集被人工判定为“错误”或经过大幅修改的用例作为负样本。
逻辑对比分析：系统通过差分算法对比“AI 原生输出”与“人工修正结果”，提取其中的逻辑差异点。
·知识图谱规则补齐 (KG Self-Correction)：
若错误源于“业务规则缺失”（例如 AI 不知道某个字段的特定校验逻辑），系统会自动生成一个待确认的三元组（实体-关系-实体）。
动作：审核通过后，该规则被写入知识图谱的“规则与约束层”，下一次生成同类需求时将强制生效。
·模型微调策略 (Fine-tuning / RAG Optimization)：
Prompt 调优：系统根据负样本自动调整提示词权重（如增加“严禁生成XXX”的指令）。
小样本微调：定期将高质量的“需求-修正后用例”对作为训练集，对 LLM 进行 LoRA 或全	量参数微调，提升模型对特定业务术语的理解精度。
